# Abra sua Bíblia!

A website to read the Bible in the translation of your choice: https://www.abrasuabiblia.com.br

Built with TypeScript, [Svelte 5](https://svelte.dev) (without SvelteKit) and [Vite](https://vite.dev), deployed on
[Vercel](https://vercel.com).

## Language policy

All source code and documentation in this project (comments, identifiers, tests, README and any
other docs) must be written in **English**. The exceptions are the translations of the user
interface (`src/i18n/locales/`, see [Interface languages](#interface-languages)), the Bible data and
the test fixtures that depend on them, which are in Portuguese.

## Development

Requires Node.js 24.

```bash
npm install
npm run dev        # development server
npm run build      # production build into dist/
npm run preview    # serves the production build (needed to test the service worker)
```

To reproduce the Vercel environment locally (uses `vercel.json`):

```bash
npm i -g vercel
vercel dev         # development
vercel build       # build identical to production, into .vercel/output
```

## Tests

```bash
npm run check      # typecheck + lint + unit tests
npm run test:e2e   # end-to-end tests (Playwright) against the production build
```

On the first run of the E2E tests, install the browser with `npx playwright install chromium`.

The tests read the Bibles from a local copy (`.bibles-cache/`, not versioned) that is downloaded
from the Blob store (see [Bibles](#bibles)) and checked against the catalog: `npm test` does it
by itself and `npm run test:e2e` runs `npm run bibles:fetch` first. The first run downloads ~120 MB
(740 MB once uncompressed); the next ones only check the files. The build of the site does not need
the Bibles.

## Dependencies and `npm audit`

No production dependency has a known vulnerability (`npm audit --omit=dev`). What `npm audit`
still lists is only in the build tooling and does not ship to the site.

`package.json` pins two versions (`overrides`) because of transitive dependencies:

- `glob` ^14.0.3: `workbox-build` 7.4.1 (the latest 7.x) uses `glob` 11, which is deprecated and
  vulnerable;
- `minimatch` ^11.0.4: fixes the glob-pattern DoS (GHSA-g3hv-75wg-m249) in `eslint`,
  `typescript-eslint` and `workbox-build`.

If an update of `eslint`, `typescript-eslint` or `workbox-build` starts requiring a different
version of either, remove the override and run `npm run check` and `npm run build`.

Accepted risk: `deepmerge` 4.3.1 (prototype pollution in `mergeObject()`, low severity,
GHSA-gcqx-w48m-w2h4), used by `@rollup/plugin-node-resolve` inside `workbox-build` and
`vite-plugin-pwa`, and by `@sveltejs/vite-plugin-svelte`. There is no fixed version (4.3.1 is the
latest), and it only merges the build options, which are ours. That is why `npm audit` still shows
5 low-severity vulnerabilities (`deepmerge` and the four packages that depend on it). Reassess when
`workbox-build` or `@sveltejs/vite-plugin-svelte` switch dependencies.

## Structure

```
index.html              page (Vite entry point); its <body> is drawn by src/App.svelte
settings.json           site configuration (default Bible, default interface language, Blob store)
bibles-catalog.json     catalog of the Bibles (generated by scripts/catalog.ts; see Bibles)
src/
  core/                 pure logic: EBF1 format, references, rendering, search, XML
  data/                 loading of the index and of the Bibles
  router/               SPA router (History API), independent of the screens
  screens/              screens; reader/ is the reading one (/{bible}/{book}/{passage}): Reader.svelte
                        draws it, reader.svelte.ts holds its state and actions; about/ is the About
                        page and help/ the Help one; navigation.ts, the navigation of the main menu
  ui/                   theme, messages, preferences; components/ (language combobox, modal...) and
                        dialogs/ (the modals of the reader) in Svelte
  i18n/                 interface languages: i18next setup, detection, flags and locales/*.json
  sw/                   service worker (Workbox)
  App.svelte            SPA shell: draws the screens and the main menu and registers their routes
  app.ts                start: interface language, theme and mounting of App.svelte
public/                 copied unchanged into the build
  assets/data/          index.json, generated at build time (the Bibles are not here)
  assets/icons/
  manifest.json
scripts/                catalog.ts, fetch-bibles.ts, build-index.ts (generates index.json), check-dist.mjs
tests/                  unit tests (Vitest)
e2e/                    end-to-end tests (Playwright)
```

## Interface (Svelte)

The interface is made of [Svelte 5](https://svelte.dev) components, with runes (`$state`,
`$derived`, `$props`). The pure logic stays out of them, in plain TypeScript (`src/core/`,
`src/data/`, `src/router/`); the state shared by the components is in `.svelte.ts` modules (e.g.
`src/screens/reader/reader.svelte.ts`). The styles of the reader are global, in `src/styles/style.css`;
the newer components (main menu, Help and About pages) keep theirs in their own `<style>`.

`npm run typecheck` runs `svelte-check`, which checks the `.ts` files and the components (including
the translation keys passed to `t`). ESLint also lints the components (`eslint-plugin-svelte`),
except for the `no-unsafe-*` rules there: typescript-eslint does not know the types of imported
components, which `svelte-check` does check. The unit tests of components mount them in jsdom
(`mount` from `svelte`, e.g. `tests/ui/text-search.test.ts`).

## Screens and main menu

The site is a single page (SPA): the router (`src/router/`) shows the screen of the URL and hides
the others, without reloading the page. The main menu (☰, `src/ui/components/MainMenu.svelte`, a
popover drawer) leads to the Bible (the reader) and to the pages, each item with an emoji:
📖 Bible, ❓ Help (`/help`: what each button does, how to type a reference and how to install the
site as an app on Android and iOS), ℹ️ About (`/about`). The paths of the pages are in English, the same in every interface language.

From any page, going back always returns to the Bible (`src/screens/navigation.ts`): a page is
always one history entry above the reader. Opening a page from the reader creates an entry, opening
another page replaces it, and a page opened directly (link, new tab) gets the reader's last reading
(`/`) behind it. The Bible item of the menu, on a page, is the same as Back.

## Bible references and passages

A **Bible reference** is the address of a passage (book, chapter and verses: `Jo 3,16-18`); the
**passage** is the text it points to. The code keeps apart the two references involved in each
passage displayed, which can differ:

- **input reference**: what the user wrote, in the reference field or in a link, e.g.
  `joão 3, 18.16.17`. Its canonical form only swaps the book for the Bible's abbreviation
  (`Jo 3, 18.16.17`) and is what goes into the field and the search history. In the URL the book is
  its USFM id instead, in lowercase (`/por/ave-maria/jhn/3, 18.16.17`), the same in every
  translation; a book read from a URL is looked up by USFM id first, then by abbreviation or name,
  and the URL is corrected to the USFM id. The book is a single word: a book whose name has spaces
  (`1 Coríntios`) is written by its abbreviation (`1Cor`) or USFM id (`1CO`). Besides the comma
  notation (`Mt 5,3-12.21-38`, dots between the parts), the colon notation is accepted
  (`Mt 5:3-12,21-38`, commas between the parts), and ranges may use an en or em dash
  (`Mt 5,3–12`). The reference is parsed with regular expressions only; anything outside the format
  (`Jo 3,abc`, `Jo 3,16.`, `Jo 3:16.17`, numbers over 3 digits) is an invalid input reference, and
  the field turns red;
- **resulting reference**: the compacted reference of the verses actually displayed, e.g.
  `Jo 3,16-18`. It is shown after the passage (with the `()` option), in the page title and when
  sharing.

The help on how to type a reference (`src/screens/reader/instructions.ts`, shown on the Help
page and in place of the passage when the reference is invalid) writes its examples with the books of the
open Bible (`Mt 5,13` in one, `Мф 5,13` in another), so that every example works when typed.

The passage is built (`src/core/passage.ts`) from the input reference and the display options
into a structure independent of the output format, which carries the resulting reference and is
then rendered (`src/core/render.ts`) as HTML for reading and as plain text for copying. See
`src/core/reference.ts` for the details.

Verses with cross-references (`references` in EBF1, e.g. in the Almeida Revista e Atualizada) end
with a balloon in the HTML (never in the copied text). Clicking it opens a modal listing them, with
consecutive verses of the same chapter grouped (`Mc 10,7-8`) and the text of each one; clicking a
reference opens it. A book the Bible lacks is listed by its USFM id and cannot be opened. See
`src/core/cross-references.ts`.

## Interface languages

The texts of the interface are translated into 17 languages, which are also the languages of the
Bibles: the list of translations only offers the ones in the interface language (plus the one
currently open, if it is of another language, since a link may open any Bible and changing the
interface language does not disturb the reading). They use
[i18next](https://www.i18next.com), with one file per language in `src/i18n/locales/`, named by the
ISO 639-3 code (`por.json`, `eng.json`, `zho.json`...). Portuguese is the reference: its keys type
`t()` and `tests/i18n` fail if another language lacks a key, has an empty text, changes the
placeholders (`{{count}}`) or lacks a plural form that its language uses.

The language shown is, in order of priority:

1. the one the user chose in the combobox, saved in `localStorage` (`uiLanguage`);
2. the first language of the browser (`navigator.languages`) that has a translation;
3. the default language of `settings.json` (`defaultLanguage`, below).

The components use `t('some.key')` from `src/i18n/reactive.svelte.ts`, which makes them render
again in the new language when it changes (the pure logic uses `t` from `src/i18n`). The few texts
of `index.html` (title, `<meta>` tags) are marked with `data-i18n` (text), `data-i18n-html`,
`data-i18n-title`, `data-i18n-placeholder`, `data-i18n-aria-label` and `data-i18n-content`
(attributes). Arabic and Urdu are right to left: the page receives `dir="rtl"` and is mirrored, while the
Bible text keeps its own direction (`dir="auto"`).

To add a language:

1. add it to `UI_LANGUAGES` in `src/i18n/languages.ts` (ISO 639-3 code, BCP 47 tag, native name and
   direction) and keep the list alphabetical by code, which is the order of the combobox;
2. create `src/i18n/locales/<code>.json` with the same keys as `por.json`, and import it in
   `src/i18n/index.ts`;
3. add its flag in `src/i18n/flags.ts` (from [flag-icons](https://github.com/lipis/flag-icons)).

`npm run check` tells what is missing. The page title, `<meta>` tags for link previews and
`manifest.json` are static, in Portuguese; only `<title>` and the `description` change with the
language.

## Bibles

The Bibles are in the [Easy Bible Format (EBF1)](https://github.com/natanael127/easy-bible-format),
published exactly as they are so that they can be downloaded and used in other projects. They are
**not in this repository and not in the deploy**: they live in a public
[Vercel Blob](https://vercel.com/docs/vercel-blob) store (`biblesUrl` in `settings.json`), one file
per Bible at the root of the store, named as in the catalog (`por_ave_maria.ebf1.json`). The browser
fetches the Bible that the reader opens straight from there (the store allows CORS and sets
`Cache-Control`), and the service worker caches it like the rest of the site.

`bibles-catalog.json` (versioned) is the list of the Bibles that the site offers. For each one it
has the file name, `name`, `language` (ISO 639-3), `slug` (the URL identifier), type
(Catholic/Protestant, by the number of books), size and SHA-256. All of it, except the file name,
comes from the content of the file (`bible.name`, `bible.language`, `bible.slug`, number of
`bible.books`), never from its name. The `slug` is optional in the EBF1 schema but required here
(`"language": "por", "slug": "ave-maria"` → `/por/ave-maria`, which opens at
`/por/ave-maria/jhn/3,16`). The catalog script fails if any of the three is missing, if a name is
repeated or if a slug is repeated within the same language.

On every `npm run build` and `npm run dev`, `scripts/build-index.ts` generates
`public/assets/data/index.json` (not in git) from the catalog and `settings.json`, with the `url` of
each Bible in the store, followed by `?v=` and the start of the SHA-256: the store ignores the query,
but it makes the browser fetch the Bible again when it changes. `scripts/check-dist.mjs` runs at the
end of every build and fails if anything but `index.json` ended up in `dist/assets/data`.

The tests validate every Bible against the official schema (`ebf1-schema.json`), which comes from the
format's repository as an npm dependency pinned to a commit (`easy-bible-format` in `package.json`).
To update the schema, change the commit hash and run `npm install`.

To add, change or remove a Bible:

1. `npm run bibles:fetch` brings the local copy (`.bibles-cache/`) up to date;
2. put the `.ebf1.json` file there, or change or delete it. The file name does not matter to the
   site, but keep it unique;
3. upload it to the store with the same name and **without a random suffix** (Vercel dashboard,
   Vercel CLI or `@vercel/blob`; an existing file has to be overwritten);
4. `npm run bibles:catalog` regenerates `bibles-catalog.json` from the local copy (`--prune` accepts
   Bibles that were deleted on purpose) and tells what was added, changed or removed;
5. commit the catalog. To check that the store has exactly what the catalog says, delete
   `.bibles-cache/` and run `npm run bibles:fetch`: it fails if any file differs.

The Bible opened on the first visit is set in `settings.json`, by language and slug (`defaultBible`).

The interface language used when the user has not chosen one and the browser's has no translation
is also set in `settings.json`, by the ISO 639-3 code of one of the interface languages. The build
fails if it is not one of them. `biblesUrl` is the https URL of the Blob store, without the trailing
slash:

```json
{
    "defaultBible": "por/ave-maria",
    "defaultLanguage": "por",
    "biblesUrl": "https://<store>.public.blob.vercel-storage.com"
}
```
